
- Hierarchy: client_projects → analysis_groups (one savings analysis) → energy_analyses rows (one PPE each). Aggregates, PPE selection, duplicate-PPE checks and the multi-PPE report are scoped to a single analysis_groups row; never sum across groups. Why: a client can hold independent alternative offers.
- energy_analyses.analysis_group_id is filled by a DB trigger when missing (creates a group with id = row id) and must point to a group of the same client project. Why: keeps old app versions and legacy rows (backfilled the same way) working.
- Aggregate (multi-PPE) totals live in src/lib/project-totals.ts and only sum results of calculateEnergyCosts; never duplicate cost formulas there. Why: single-PPE engine stays the one source of truth.
- Unit tests run with `npx vitest run --root . src/lib`. Why: no test script in package.json.
- Value provenance lives in energy_analyses.value_sources (field -> {source, rate_card_id?, document_id?, page?, item_ref?}) plus rates_source_*/rates_year_* snapshots; rules in src/lib/value-sources.ts. Missing entry = unknown, never infer for legacy rows. Auto-fetch of rates must go through canAutoApplyRates. Why: base rates must never silently overwrite manual or document values.
- cost_mode_before: only 'rates' is implemented; 'invoice_actual' is reserved and must not be selectable until its engine exists. Why: no fake features.
- Invoice import (stage 2): analysis_documents + document_ppe_records + document_line_items scoped to analysis_groups; files in private bucket invoice-documents under {groupId}/{docId}/; AI parse only in edge function parse-invoice (Gemini via Lovable AI Gateway); UI applies only user-approved PRZED fields, never PO; approval idempotent via applied_at + .is('applied_at', null). Why: no silent overwrites, no duplicate applies.
- Invoice line items map to PRZED fields only via explicit rules in src/lib/invoice-line-mapping.ts (category + unit + basis), converting to the engine's field units (variable distribution: C/G zł/kWh, B/A zł/MWh); fees without a matching engine field stay unsupported. Why: no double ×1000, no fake savings from PRZED-only fees.
- Invoice items without a dedicated field may go to fixed_distribution_before_total only as summed net amounts per PPE via planOtherCharges (src/lib/invoice-line-mapping.ts); contributions are stored in value_sources.fixed_distribution_before_total.breakdown and re-imports of the same document replace their earlier contribution. Why: no double counting, explicit replace/add choice.
- Re-editing an approved invoice import goes through planReapply (src/lib/invoice-reedit.ts) using document_ppe_records.review_state (user choices + before/after snapshot); sums recompute only this document's breakdown contribution; fields changed manually after import are never overwritten or reverted without explicit user consent. Why: no double apply, no silent loss of manual edits.
- Invoice tariff codes map to the calculator dictionary only via normalizeTariffCode, and consumption zones only via mapConsumptionZones (zone meaning from name, never row order; missing zone = no data). Why: unknown tariffs must not fall back to a default, consumption must not be split by guess.
- Subscription (abonament) and handling-fee invoice items feed handling_fee_before as a monthly amount via planHandling/monthlyAmount (src/lib/invoice-line-mapping.ts): different components are summed, repeats of the same fee count once, differing rates or unclear periods block apply. Why: the field is zł/month, never a multi-month total.
- Multi-invoice settlement per PPE is computed on the fly by buildSettlement (src/lib/invoice-settlement.ts) from approved records and selected items; never stored as running totals. Why: re-saves can't duplicate.
- Individual feature flags live in protected user_feature_access with trigger-written feature_access_history; UI consumes useFeatureAccess, database triggers serialize PPE cardinality and preserve read access, and parse-invoice rechecks current permission before each paid request. Why: role membership is not a feature grant and frontend controls cannot enforce authorization.
- Destructive client actions use delete_client_object with explicit owner/admin authorization and transactional scoped cascades; invoice_file_cleanup is queued within deletion and processed after commit by cleanup-invoice-files, retryable on subsequent deletion or explicit invocation. Why: feature flags must not block authorized deletion and storage errors must not partially delete database data.

- AI assistant: model calls only in edge function ai-assistant (rechecks has_feature_access('ai_assistant') + can_access_analysis_group, reads PPE with user JWT; ai_conversations/ai_messages/ai_usage_log written only by service_role). Results come from browser calculateEnergyCosts per PPE at send time (draft as '<id>__robocze'), forwarded only for PPE the function read. Why: no bypass of flags/RLS; model quotes UI numbers.
